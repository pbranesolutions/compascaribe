# CLAUDE.md

Working notes for agents and people editing this repository.

## Shape

- Vanilla JS modules + plain CSS, built with Vite 8 (a dev dependency), deployed as Cloudflare Workers static assets (`wrangler.jsonc`). No framework. The one runtime dependency is the official `@anthropic-ai/sdk`, imported only by `src/domain/conversation/opening.js` (server). The only server code is the Worker routes `POST /api/gate` and `POST /api/conversation` (`worker/`).
- `src/domain/*` is pure logic with node tests; `src/ui/*` renders journey state; `src/app/journey.js` owns transitions. Keep that separation: the UI never imports `discovery/simulated.js` directly, only `provider.js`.
- The Jev gate (`src/domain/gate/*`, `worker/gate-handler.js`) and the conversation (`src/domain/conversation/*`, `worker/conversation-handler.js`) are the live AI steps. Begin runs the gate; PROCEED that carries the server's qualification opens the conversation (one Claude request for the first reply, then one for every answer the visitor sends); BLOCK and UNAVAILABLE stay at `src/ui/diagnostic.js` and never reach a model. Never put a canned or simulated result in either path; tests inject fakes, production does not.
- Generation only follows a server-issued qualification for the exact words. Do not add another way to reach `generateOpening` / `generateTurn`, do not enable SDK retries or fallback models without changing the request contract below, and keep `opening.js` out of anything the browser imports (`tests/conversation-boundary.test.js` enforces it).
- Request contract: one model request per reply. The only extra request is the bounded repair in `generateTurn`: a follow-up whose reply fails `validateTurn` is asked for once more with the reason (`turnRepairs`, only while there is time; never for refusals, timeouts or transport errors). The opening is never repaired.
- The conversation's cost is bounded by signed data, not by what the browser says: every reply returns a renewed qualification carrying the number of replies (`n`) and the conversation's start (`x`); the server uses `max(signed count, history length)`, tells the agent to converge after `convergeAfter`, makes the last permitted reply (`maxReplies - 1`) a statement and refuses beyond it (`limit`). Defaults are in `src/domain/conversation/config.js`.
- The conversation is customer-facing: no engineering labels (model, "live", "written by an AI model") in it. Say AI-assisted once, quietly; put diagnostics behind `?diagnostics` (`.conv-diag`, top-bar labels).
- The agent's voice lives in `src/domain/conversation/prompt.js` and nowhere else (`SYSTEM_PROMPT` for the first reply, `TURN_SYSTEM_PROMPT` for the rest); what a reply must look like lives in `schema.js` (`validateOpening`) and `turn.js` (`validateTurn`, the understanding, the statement). Visitor text and the history it travels in are untrusted: they are passed to the model inside tags and displayed only as text.
- The conversation is stateless on the server: the browser holds `ctx.conversation.turns` (and sends them back, bounded by `history.js`), and each follow-up carries the agent's own working understanding so it builds on the last. The understanding is the record of the whole project, not of the last answer (`UNDERSTANDING_LISTS` in `turn.js`): `objectives` (one entry per distinct thing the project is for; an objective leaves only through `dropped`, by the visitor's words), `beneficiaries`, `outcomes`, `evidence` (incidents, examples, numbers, constraints: illustrations, never objectives), `inferred`, `open`, `coverage`. Every turn also carries a private `rationale` (what is understood, what is materially unclear, why this question or why the statement now). The opening records `objectives` too, which seed the first follow-up. The visitor's words and answers are never rewritten.
- The statement must cover every objective not dropped, keep stated facts and constraints even when the visitor did not tie them to the goal, and keep inferences out; a correction changes exactly what was corrected. A follow-up's reflection is optional: it earns its place by connecting or clarifying, never by paraphrasing. The regression for all of this is `npm run test:live:flow` (scenarios `apartment`, `three-objectives`, `anecdote`, `adds-objective`, `clear`, `corrects`), which checks the final statement against pattern groups per objective and asks a judge about scope and unnecessary questions.
- The conversation ends in a statement of the project's purpose that the visitor confirms or corrects. Confirmed, it becomes `ctx.statement` (source `conversation`) and the way on is Continue into the simulated handoff. Everything after that (the handoff, Decision Channel) is simulated and labelled as such. Do not add code that pretends a network call, account or Decision Channel project exists.
- `TYPESAFE_API_KEY` and `ANTHROPIC_API_KEY` are server-side only (Worker secrets / `.dev.vars`). Never reference them from `src/` UI code, logs or responses.

## Non-negotiable: zero scrolling

- No element may scroll: no `overflow: auto|scroll`, no scrolling textareas, no transcript lists. Fit text (`fitText`), page it (`pagedText`, `pagedList`), or disclose it in an overlay.
- Every new text block needs a bounded height (a grid track or a `max-height`) so the fitter can act.
- The conversation (`src/ui/conversation.js`, the `.conv` section of `app.css`) is one flat grid with named areas composed per viewport from the same DOM: phone (project / reading / field), short-and-wide (project + reading | field), tall tablet (… / exchanges so far below), desktop (reading + field | a panel with the project and the exchanges so far). Reading sizes come from CSS `--fit-min`/`--fit-max` and the `--q-max`/`--r-max`/`--st-max` caps per breakpoint; keep them such that the field fits at rest without the `budget()` fallback. A grid track that is too short squeezes a `min-height: 0` item without clipping, so the audit cannot see it: `budget()` checks the reply column and the composer for interior overflow, and the harness checks the Send button sits inside its card (`sendInside`).
- Verify with the browser harness, not by eye: `npm run dev`, then `node tests/browser/run.mjs`. It must report 0 failures across all viewports before a change is done. `?audit` in the dev URL logs overflow after each render.

## Commands

- `npm test` — domain, gate, conversation and Worker tests (mocked; must pass). `npm run test:live` makes real Jev calls, `npm run test:live:conversation` runs Jev then real Claude first replies and prints them for review, and `npm run test:live:flow` runs whole multi-turn conversations against simulated visitors (vague, contradictory, terse, off-topic, Spanish…) through the real Worker handler with a judge (about 0.5 USD); all skip without keys.
- `npm run build` — must succeed.
- `node tests/browser/run.mjs --url http://localhost:5173` — zero-scroll and journey checks in headless Chrome (needs Chrome/Edge installed).
- Never run `npm run deploy` without being asked; it ships to production.

## Copy

- English, second person, no marketing superlatives, no praise of the visitor. Reflections ≤150 chars, questions ≤90, options ≤46, statement ≤360 (enforced in tests).
- The same standards bind the live agent in its own limits (`OPENING_LIMITS`, `TURN_LIMITS`): one question, no praise or filler, nothing the visitor did not say, no budget/technology/feature questions, the statement one to three sentences and every claim traceable to their words. Verify any wording change with `npm run test:live:flow` (whole conversations, a simulated visitor, a judge) and read the transcripts.
- The company name is always "Compás Caribe"; "Decision Channel" is a separate, connected platform.
- The length limits above govern authored (simulated) copy. The live first reply is held to `OPENING_LIMITS` in `src/domain/conversation/schema.js` (about 30 to 70 words, hard caps 60 + 45) and answers in the visitor's language; the interface around it stays English.
